# Design: Release Claude Code 2.1.310

## Context

The scope is in `proposal.md`, and the behavior is in `specs/tracked-release-docs/spec.md`.
`release:check` and `release:diff` ran on 2026-10-24: `check ok`, and the counts in `prd.md`.
`captures/2.1.309/` holds the old print and pty results, so `compare` has a baseline.

## Decisions

1. **Run `release:all -- --from 2.1.309 --to 2.1.310` once, then read the worklist.** It reruns check and diff, which is cheap, and gives one `run.json`. Alternative: run each step by hand, which is only needed after a failed step.
2. **Sort each worklist and diff item as change or noise before any edit.** Rerun a changed case on both versions to split them, as for 2.1.309. Alternative: edit from the first result, which let pty timing noise into pages before (the runbook's `invalid-run` rule).
3. **The 8 `claude-3-*` model ids need a reason before a row.** They may be a retired-model list or an alias table. Read their module with `cc-inspect` first. Add rows only when a user can pick or is affected by the id. Otherwise add an exclusion. Alternative: add rows at once, which could state a model as usable when the program only names it to refuse it.
4. **Env vars with a `CLAUDE_TEST_` prefix go to exclusions as test-only**, unless the code reads them outside a test path. Same rule as the existing test-only exclusions. The 4 `CLAUDE_CODE_*` vars get rows with `<Undocumented />` when a user can set them.
5. **New artifact and doc-write errors** (`read_comments`, "Write not done", "Write refused") belong to the artifacts surface. Place them on the page that covers artifacts tools today, found with `grep`. If none covers it, use an exclusion with the reason "no page covers the artifacts tools yet". Alternative: a new page, which is out of scope for a release.
6. **Gates stay under the gate exclusion.** `tengu_cobalt_plinth_larch` (default now `true`) gets a page row only if `cc-inspect` shows it guards a documented behavior. The Monitor provider change is checked the same way, because the notes item may be a gate.
7. **Labels change file by file, with a check of each fact**, not by search and replace. Use the 2.1.309 method: `grep -rn '2\.1\.309' docs`, then keep change notes and dated records.
8. **Live probes run last** (`architecture.md` decision 3). Managed probes wait for the user.
9. **Clean names by scope order.** Each binding a module declares gets a name from its scope depth and declaration order (such as `f3_a2`). Exports, imports, property names, and strings keep their text, and chunk names become a hash of their export names. The same code in two builds then prints the same text, so a diff shows only real changes. Alternative: keep the minified names, where each release renames most of them and the diff is noise.
10. **Match units in stages, with names ignored.** Names are left out of each comparison, because a local's number moves when an outer scope gains a name, and a module-level name moves when its declaration changes. Stages: equal text (with the label, and for a unit with no literals also the same parent), equal fingerprint (sorted literals and property names), label under the same parent fingerprint, literal overlap of 0.6 or more, and label under a paired parent. A pair with equal text is unchanged. Imports and exports are left out, because chunk splitting moves them in every build. Each change lists the string constants of its enclosing code and the literals of the small functions it calls, followed across chunk imports, so `name` finds a tool by the string its `name` constant holds. Alternative: match by position, which breaks when chunks move.
11. **"How" comes from the function body.** A no-op returns a constant only (`()=>!1`, `()=>{}`). A stub throws or returns a constant after a check of a gate or env name. Handled code does anything else. "When" lists the gate names (`tengu_*`), env reads, and `isEnabled` that guard it. "Who" lists the callers that `callsOf` finds. Alternative: a model summary, which is not a fact.
12. **Release notes come from `gh release view v<version> --repo anthropics/claude-code`**, cached in `captures/<version>/notes.md`. A line matches a change when one of its code spans is in the change's strings (2 points each), the line names the change's subject (its object's `name`, 2 points), or 3 or more of its words of 5 letters or more are in one string the change adds or removes (1 point each); a `release:diff` item matches the same way. A score under 2 is unmatched, a tie goes to the smaller change, and a match whose code reads a `tengu_` gate is gated. A scope prefix such as `[VSCode]` is left out, because it says where, not what. Alternative: free-text search, which finds too much.
13. **Output stays small.** Each tool returns a summary first and caps the code it shows (40 lines for each function, 30 functions for each call), with a `name` filter to see more. Why: the goal is a release with few tokens.
14. **Wakaru is an optional reading view, not part of the diff** (task 5.1). `@wakaru/cli` 1.14.0 reads Bun executables, keeps `using` declarations, parses back, and recovers some names from destructured fields, but takes 6.15 s on the largest chunk against 0.21 s for `bun fmt`, and it is a separate Node package that the plugin bundle cannot carry. So the diff uses the scope names and `bun fmt`, and a `view: "readable"` option runs `bunx @wakaru/cli@1.14.0` on one module when asked, cached under `captures/<version>/clean/readable/`. Alternative: Wakaru in the pipeline, which makes every release slower and adds a dependency to the diff.
15. **`find` ranks by word hits, and prompts carry the steps.** The `code` action `find` splits a query into words, and scores each unit by the words found in its strings, property names, and label (an exact property name counts 2, any other hit 1), with a half point for a word found only in its cleaned text, such as a regular expression, then by shorter text. It returns the top 10 with module, offset, and a few lines. MCP prompts `release_review` (`code` `prepare` for both versions, `release` `diff`, `release` `notes`, then `find` and `explain` for each unmatched or gated item) and `explain_change` (one name through `find` and `explain`) let an agent run a release with no plan of its own. Why: an agent can ask in plain words and still get program facts, with no model call inside the server. Alternative: embeddings or a model inside the server, which costs tokens and is not a fact source.
16. **4 tools, each with an `action` or `kind`** (the user, 2026-10-24: "consolidate related tools using parameters instead of separate tool definitions", and one concise sentence for each description). `sessions` (list, read, search, validate), `code` (installs, modules, search, read, prepare, find), `surface` (each surface kind, plus `object-keys`, `event-keys`, and `tool-gates`, named apart from the kinds `tool` and `otel-event`), and `release` (diff, explain, notes). Shared names: `version` (was `binary`), `query`, `name`, `limit`. An unknown `action` returns the list of actions. Why: 12 separate tools (17 with the planned ones), many alike, are past the 10 to 20 where a model starts to confuse tools; the user also asked not to hide tools. Alternative: 2 or 3 tools, which gives one tool 9 to 13 actions.

## Risks / Trade-Offs

- [Notes item missing from the binary, for example a server-side change] -> Leave it out and list it in the tasks.
- [Pty timing noise looks like a change] -> Rerun once on both versions. Never edit from an `invalid-run`.
- [Prompt render churn, such as random UUIDs] -> Review `git diff docs/prompts/` and keep only real prompt changes.
- [149 files to relabel] -> Split the sweep by docs section. Use one Worker at a time while the weekly band is red.
- [Live probes use up the weekly limit] -> Run them only when the band is not red. Until then, mark live-only claims unverified.
- [A removed name still on a page other than Surface Coverage] -> `grep` each removed name across `docs/` before the commit.
- [Cleaning 2 installs is slow or uses much memory] -> Clean once per version, cache it, and time it in task 5.3.
- [Fingerprint matches pair the wrong functions] -> Test with two builds of a fixture app, and check the Monitor `isEnabled` change on the real pair.
- [The weekly band is red] -> One Worker at a time; the paid `humanify` trial runs last.
